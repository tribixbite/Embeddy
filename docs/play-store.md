## 1. Back up the keystore (do this first)

If this file or its password is lost, Play installs can still be updated (Play
holds the signing key after step 4), but GitHub and F-Droid installs never can.
The GitHub secret is not a backup — secrets cannot be read back.

```sh
# Confirm the password you have on record opens it (prompts for the password)
keytool -list -v -keystore ~/git/embeddy-release.jks -alias embeddy | rg 'SHA256:|Valid'
# Expect SHA256: 61:2C:62:1B:...:2E:94:FE
```

Copy `~/git/embeddy-release.jks` plus its password into your password manager
or another offline location. If the password does not open it, stop here: the
CI secret still works for signing, but you need the password for step 4.

### Switch Play to our release key (done 2026-11-02)

The keystore password is only in the GitHub secrets, so the export runs in CI
(`.github/workflows/play-key-export.yml`). pepk encrypts the key with Play's
public key, so only Google can read the resulting zip.

1. Play Console → **Test and release → App integrity → App signing →
   Change key** (shown only while no release has gone live) → choose
   **Export and upload a key from Java keystore** → download
   `encryption_public_key.pem` into `~/storage/downloads`.
2. Run the export and fetch the encrypted zip:

   ```sh
   cd ~/storage/downloads
   gh workflow run play-key-export.yml --repo tribixbite/Embeddy \
     -F encryption_public_key=@encryption_public_key.pem
   sleep 10
   RUN=$(gh run list --repo tribixbite/Embeddy --workflow play-key-export.yml \
     --limit 1 --json databaseId --jq '.[0].databaseId')
   gh run watch "$RUN" --repo tribixbite/Embeddy --exit-status
   gh run download "$RUN" --repo tribixbite/Embeddy --name embeddy-play-signing-key
   ls -l embeddy-signing-key.zip
   ```

   The job refuses to run unless the keystore's certificate is `61:2C:…:94:FE`
   and pepk.jar matches the pinned hash.
3. On the same page, upload `embeddy-signing-key.zip` and save. App signing
   should then show the app signing key SHA-256 as `61:2C:62:1B:…:2E:94:FE`.
4. `rm embeddy-signing-key.zip encryption_public_key.pem` (the artifact
   expires after a day).

If you would rather run pepk yourself with the keystore password, the page
shows the command; use `--keystore="$HOME/git/embeddy-release.jks" --alias=embeddy`.

## 5. Get the bundle

The release workflow builds it on every app change. Download the newest one:

```sh
cd ~/storage/downloads
RUN=$(gh run list --repo tribixbite/Embeddy --workflow release.yml --status success \
  --limit 1 --json databaseId --jq '.[0].databaseId')
gh run download "$RUN" --repo tribixbite/Embeddy --pattern 'embeddy-v*-play-bundle'
ls embeddy-v*-play-bundle/

# Confirm it is signed with the release key (expect SHA256: 61:2C:...:94:FE)
keytool -printcert -jarfile embeddy-v*-play-bundle/*.aab | rg 'SHA256:'
```

Artifacts expire after 90 days; download the one you are about to publish.

### Data safety form

Submitted 2026-11-03 as **"Does your app collect or share any of the required
user data types? No"** — the store shows "No data collected" and "No data
shared with third parties".

Owner's reasoning: the developer receives nothing. The app has no analytics,
crash reporting, ad SDK or backend of ours. The only network traffic is a file
the user explicitly sends to a host they pick (`upload/UploadEngine.kt`: 0x0.st
or catbox.moe; any file type via `*/*`, so photos, video, audio and documents)
and a URL the user typed for Inspect (`inspect/MetadataEngine.kt`, fetched
directly from the device).

How that maps onto Google's text
(<https://support.google.com/googleplay/android-developer/answer/10787469>):
transfers "based on a specific user-initiated action, where the user
reasonably expects the data to be shared" are exempt from *sharing*. The
*collection* definition is literal — "transmitting data from your app off a
user's device … irrespective of whether data is transmitted to you or a
third-party server" — and its only listed exemptions are on-device processing
and end-to-end encryption. If a reviewer reads Upload as collection, the
stricter answer is: Photos, Videos, Music files, Other audio files, Files and
docs — collected **yes, optional**, shared **no**, not ephemeral, purpose *App
functionality*, encrypted in transit yes, no deletion request (we hold
nothing). Revisit if a network feature or SDK is added.

## 7. Closed test (only if step 2 says it applies)

1. **Test and release → Testing → Closed testing → Create track** (or use the
   default *Alpha* track).
2. **Testers**: add an email list or a Google Group with **at least 12** people
   (aim for 15–20; anyone who opts out during the 14 days stops counting).
3. **Create release** → upload the `.aab` from step 5. Release notes: paste
   `fastlane/metadata/android/en-US/changelogs/<versionCode>.txt` for that
   release (`ls fastlane/metadata/android/en-US/changelogs | tail -3`).
4. **Review release → Start rollout to Closed testing.** First review usually
   takes a few days.
5. Send testers the opt-in link from the track's **Testers** tab. They must
   accept it with the Google account on their phone, then install from Play.
6. Keep ≥ 12 testers opted in for **14 consecutive days**. Upload a newer
   bundle during the test if you can — Google's production-access form asks
   what you changed based on tester feedback.
7. After day 14: **Dashboard → Apply for production** and answer the
   questionnaire (who tested, what feedback, what changed, why it is ready).
   Approval typically takes up to 7 days.

## 8. Production release

1. **Test and release → Production → Create release** → *Add from library*
   (reuse the tested bundle) or upload a newer `.aab`.
2. Countries: all, unless you want to restrict.
3. Start with a **staged rollout** (e.g. 20 %), watch *Android vitals* for
   crashes/ANRs for a few days, then increase to 100 %.

Later releases repeat step 5 and this step. Each CI release's versionCode is
higher than the last, so any new bundle uploads cleanly.
